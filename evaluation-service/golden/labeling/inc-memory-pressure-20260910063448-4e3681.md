## 3. 조치 계획 (action 노드)

- actions: SCALE_OUT, RESTART_APP
- rationale: 근본 원인은 target-app 내부의 메모리 누수 패턴(Old Gen 지속 축적, GC 후 미회복, 실제 OOM 발생)으로 코드 결함성 이슈다. 따라서 RESTART_APP/SCALE_OUT은 근본 수정이 아니라 임시 완화(heap 회복, 가용성 확보)일 뿐이며, 별도로 누수 컴포넌트 식별 및 코드 수정(TTL/버퍼 해제 등)이 반드시 뒤따라야 한다. 현재 replicas=1로 이중화가 없어 재기동 시 순간 다운타임이 발생하므로, 먼저 SCALE_OUT으로 replicas를 2 이상으로 늘려 가용성을 확보한 뒤 RESTART_APP으로 순차 재기동해 heap을 초기화하는 순서를 제안한다. 유사 사례(inc-2026-0619)에서도 동일 패턴에 RESTART_APP으로 완화한 전례가 있어 severity(P2)와 확신도(0.93)에 비례하는 조치로 판단된다. 근거 데이터 중 '재기동으로 chaos 상태가 초기화된다'는 설명은 fault-injection 데모 환경 특성을 설명하는 문구로, 실제 운영 환경에서의 동일 증상에도 동일한 조치(재기동+스케일아웃)가 유효함을 뒷받침한다. 근거 텍스트 내 별도의 지시성 문구나 "이미 승인됨" 류의 주장은 발견되지 않았다.
- risk: RESTART_APP: 재시작 중 진행 중이던 요청 유실 가능(특히 replicas 확장 전 단일 인스턴스 상태에서 실행 시 순간 다운타임 발생); chaos/fault-injection 상태가 재기동으로 초기화되어 데모/테스트 목적의 재현 데이터가 손실될 수 있음. SCALE_OUT: 추가 인스턴스에 따른 자원(CPU/메모리) 비용 증가, 그러나 누수 로직이 각 인스턴스에서 동일하게 재현되므로 신규 인스턴스도 시간 경과 후 동일한 메모리 압박을 겪을 수 있어 근본 해결책이 아님. 두 조치 모두 임시 완화이며 근본 원인(누수 코드) 수정이 병행되지 않으면 반복 재발 가능.
- 승인: rejected · 회복: skipped
