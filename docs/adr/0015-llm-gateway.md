# ADR-0015: LLM 게이트웨이 도입 방식 — 별도 서비스 직접 구현

- 상태: 승인됨 (2026-08-22 확정 — 비교표·실측 보강)
- 날짜: 2026-08-17

## 맥락

현재 LLM 호출은 두 갈래로 분산되어 있다 — agent-service 의 채팅 호출(langchain, Anthropic Sonnet 5 — [ADR-0007](0007-llm-provider.md))과 control-plane 의 임베딩 호출(Spring AI, OpenAI text-embedding-3-small — 유사 인시던트 검색). 이 구조에서는 라우팅(작업별 모델 차등)·캐싱·비용 집계·폴백·rate limiting 같은 공통 관심사를 Kotlin/Python 양쪽에 중복 구현해야 하고, 실제로는 대부분 미구현으로 남는다.

결정을 요구한 직접 계기는 둘이다: ① README 로드맵(2026-08)의 예고 — "게이트웨이 배치(control-plane 내장 vs 별도)는 ADR 로 결정" ② 이후 보안 작업의 전제 — prompt injection 방어의 합의 구조는 "에이전트 코드가 넘을 수 없는 경계에서 통제"인데, 모든 호출이 지나는 관문이 없으면 입출력 가드레일을 강제할 지점 자체가 없다.

제약 조건: 프로바이더는 2종(Anthropic 주·OpenAI 임베딩/교차)으로 좁고, 실 사용자 트래픽 없음(비목표)이라 성능·규모는 요구가 아니다. 학습·포트폴리오 목적이 명시된 프로젝트다.

## 결정

**LLM 게이트웨이를 별도 마이크로서비스(`llm-gateway/`, Spring Boot 4.x + Kotlin + Spring AI 2.0)로 직접 구현한다.** OpenAI 호환 API(`POST /v1/chat/completions`, `POST /v1/embeddings`)로 노출해 클라이언트 전환을 base-url 변경 수준으로 만든다. 스트리밍은 미지원(현행 사용 0건 실측 — 배제가 아닌 유예), 상태(캐시·카운터)는 전부 외부 저장(Redis·PostgreSQL)에 두어 다중 replica 를 코드 무수정으로 성립시킨다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 사유 |
|------|------|------|-----------|
| control-plane 내 모듈 | 단일 JVM·배포 단위 추가 없음 | Python 에이전트 호출이 control-plane 을 경유하는 순환 결합 (agent → cp → LLM, cp 는 이미 MCP 서버로 agent 의 도구 제공자), 장애·스케일 경계 불분명 | "모든 트래픽 단일 통과점"은 성립하나 관제 책임과 중계 책임이 단일 배포 단위에 결합 (책임 분리 위배) — 보안 주간 가드레일도 관제 코드와 같은 배포 단위에 놓임 |
| LiteLLM 도입 | 100+ 프로바이더·성숙 생태계 | Python 프록시 별도 운영, 커스터마이징은 포크/플러그인 경계 안 | 필요 기능 폭(프로바이더 2종)에 비해 과함 + 가드레일 커스터마이징이 핵심 요구 — 상세 비교표는 승인 확정(2026-08-22) 시 보강 |
| Bifrost 도입 | Go 단일 바이너리·sub-ms 오버헤드·시맨틱 캐싱 내장 | 커스텀 로직(태스크 라우팅 정책·예산 다운그레이드 규칙) 확장 경계 제한 | 동일 — 학습 목적(직접 구현으로 게이트웨이 내부 구조 체득)과 Spring 관측 스택 통합이 우선. 실무 선택 기준은 승인 시 병기 |

## 결과

- 쉬워지는 것: 라우팅·캐싱·비용·폴백·한도가 한 서비스에 수렴 — 역할별 모델 차등(ADR-0007 보류분)이 클라이언트 무수정으로 실현. 보안 주간 가드레일이 들어갈 경계 확보. CIRCUIT_BREAK 조치의 실물(게이트웨이 서킷브레이커) 등장.
- 어려워지는 것: 배포 단위 +1 (차트·이미지·관측 대상 추가), 모든 LLM 호출의 단일 장애점화 — HA(replica 2 + PDB)와 클라이언트 재시도·백오프(Kafka 재소비 복구)로 흡수 예정.
- 되돌리기: OpenAI 호환 인터페이스가 계약이라 LiteLLM/Bifrost 로의 교체는 클라이언트 무수정 — base-url 이 가리키는 실체만 바뀐다. 직접 구현의 학습 산출(비교 기준)이 교체 판단 재료가 된다.

## 추가 사항 (2026-08-20): 고가용성 방식 — replicaCount 2 고정 + PDB, HPA 기각

"모든 LLM 호출의 단일 장애점화"의 흡수 방식을 확정한다. CPU HPA(min 2) 는 metrics-server 설치가 전제인데 클러스터에 의도적으로 미설치 상태(KEDA 는 외부 메트릭이라 무관)이고, 실 사용자 트래픽 없음(비목표) 조건에서 자동 스케일의 실익이 없다 (control-plane min 1 결정과 같은 논리). 대신 **replicaCount 2 고정 + PodDisruptionBudget(minAvailable 1)** 로 자발적 중단(드레인)·단일 pod 장애를 흡수한다. replica 2 의 전제인 상태 외부화(캐시·예산 카운터·rate limit 버킷 = Redis/PostgreSQL)는 2026-08-18~19 (캐싱·비용 통제 구축)에 이미 성립했다. 비자발적 장애의 나머지 반쪽은 클라이언트 측 — openai SDK 내장 재시도(연결 실패·5xx) + LangGraph 노드 재시도 허용 목록에 게이트웨이 호출 예외(openai SDK 계열) 추가로 담당한다.

## 추가 사항 (2026-08-22): 승인 — LiteLLM / Bifrost 비교표와 실측 병기

구현 완료(2026-08-17~22) 후 확정한다. 아래 비교는 2026-08 시점 공개 문서 기준 — 8/14 사전 조사 이후 변한 사실 하나를 정정한다: LiteLLM 은 "Python 프록시"가 아니라 **Rust 코어 + Python SDK** 로 재편됐다 (공식 리포 자기 서술, P95 8ms @ 1k RPS 벤치마크 제시). 2026-03 공급망 사건 이후 "컴파일 바이너리 = 공급망 표면 축소" 논거로 부상한 Bifrost 와의 성능 격차 서사도 그만큼 좁혀진 상태다.

### 기능 비교표

| 축 | LiteLLM | Bifrost | llm-gateway (직접 구현) |
|----|---------|---------|------------------------|
| 프로바이더 | 100+ (chat 외 audio·image·rerank 등 엔드포인트 폭넓음) | 20+ | **2 (Anthropic·OpenAI)** — 요구 전부 |
| 라우팅 | 휴리스틱·LLM 분류기·시맨틱 규칙 등 다층 정책 + 로드밸런싱 | 가중 로드밸런싱 + 모델 필터링 | X-Task-Type → 규칙 테이블 (yml) — 요구 대비 등가 |
| 캐싱 | 시맨틱 캐시 내장 | 2계층 (해시 정확 + 벡터 유사, 임계 기본 0.8, Redis/Qdrant 등) | 2계층 (L1 Redis 정확 + L2 pgvector 유사도 0.95) — 구조 동형 |
| 예산 | 키·팀·사용자 단위 한도 + 예산 소진 시 무료 모델 폴백 구성 가능 | 4단 계층 (Business Unit→Team→Virtual Key→Provider) | 일별 전체·서비스별 한도 + **100% = 차단 아닌 다운그레이드** (커스텀 규칙) |
| 폴백 | 재시도·프로바이더 폴백 체인 구성형 | 자동 failover + 키 분산 | 서킷 + 교차 재중계 + 로컬 폴백 (체인 커스텀) |
| 가드레일 확장 | 내장 (콘텐츠 필터·PII 마스킹) + 플러그인 | 플러그인 (MCP 게이트웨이·승인 정책 내장) | **확장 지점만 예약 (이후 보안 작업에서 직접 구현)** — 이 결정의 핵심 요구 |
| 관측 통합 | OTel 스팬 방출 등 자체 생태계 | 자체 거버넌스 대시보드 | **기존 스택 그대로** (Micrometer→Prometheus·Grafana, W3C 전파) — 신규 관측 학습 0 |

### 실무라면 어떤 기준으로 선택할까 (판단 기준 4)

1. **필요 기능 폭**: 프로바이더가 수 종을 넘고 audio·image 등 비-chat 엔드포인트가 섞이면 직접 구현의 유지 비용이 표의 왼쪽 두 열을 정당화하지 못한다 — 그 시점엔 LiteLLM. 반대로 프로바이더 2~3종·chat/embeddings 뿐이면 게이트웨이는 며칠 규모의 구현이고(이번 주 실증), 통제 지점을 소유하는 값이 더 크다.
2. **배치·운영**: 조직에 Python/Go 운영 역량과 별도 게이트웨이 팀이 있으면 도입, JVM 단일 스택 조직이 관측·배포 파이프라인을 공유하려면 직접 구현이 마찰이 적다.
3. **관측 통합**: 기존 스택(Prometheus·Grafana·OTel)에 그대로 통합되는지 — 도입 제품의 자체 대시보드·계정 체계가 이중 관제가 되는 순간 운영 비용이 기능 이득을 잠식한다.
4. **커스터마이징 경계**: 예산 초과를 차단이 아니라 다운그레이드로 흡수하는 규칙, 폴백 응답의 캐시 오염 방지 같은 도메인 규칙이 제품의 설정 표면 안에서 표현되는지 — 밖이면 포크/플러그인 유지 비용이 시작된다. 이 프로젝트는 보안 주간 가드레일 커스터마이징이 확정 요구라 이 축이 결정적이었다.

되돌리기 비용은 결정 본문의 계약 그대로 — OpenAI 호환 표면 덕에 교체는 base-url 변경이다.

### 구현 후 실측 (2026-08-17~22)

- 캐시 히트 단축: miss 5.02s → L2 히트 0.39s (**92.2% 단축**, 8/18)
- 폴백 전환: Anthropic 무효 키 상태에서 기본(sonnet) 요청이 OpenAI(gpt-5.6-terra) 재중계로 정상 응답, 서킷 오픈(표본 4건) 후 fast-fail 1.2s (8/20)
- 가용성: 게이트웨이 pod 강제 삭제 중 S1 파이프라인 62초 완주 — replica 2 + 클라이언트 SDK 재시도의 합 (8/20)
- 게이트웨이 오버헤드: 단독 수치 미측정 (실 사용자 트래픽 없음 비목표) — 2026-08-22 장착한 캐시 분리 레이턴시 히스토그램(`gateway_latency`)이 상시 관찰 수단
