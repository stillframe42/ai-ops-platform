# ADR-0010: 운영 도구 노출 방식 — REST 직접 호출 대신 MCP 표준

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

분석 에이전트가 쓰는 운영 도구(배포 이력·유사 인시던트 검색·앱 설정)는 지금까지 agent-service 안의
로컬 더미 함수였다. 3주차에 control-plane 이 실체화되면서 이 도구들을 서버 측으로 이관하는데,
Python 에이전트가 Spring Boot 서버의 기능을 호출하는 방식을 정해야 한다. 제약 조건:

- 도구는 계속 늘어난다 (4주차 조치 실행, 8월 k8s 도구) — 추가할 때마다 양쪽 코드를 고치는 구조는 피하고 싶다
- 도구 스키마(이름·파라미터·설명)는 LLM 이 직접 소비한다 — 스키마 정의가 이중화되면 어긋난다
- 8월 보안 주간에 도구 접근 권한 체계(OAuth 2.1)를 얹을 예정 — 표준 위에 있어야 재사용할 게 많다

## 결정

control-plane 의 운영 도구를 **MCP(Model Context Protocol) 표준으로 노출**한다.
Spring AI 2.0 `spring-ai-starter-mcp-server-webmvc` (Streamable HTTP — SSE 는 2.0.0 부터 deprecated 라 사용 금지),
Python 쪽은 `langchain-mcp-adapters` 로 도구를 프로토콜로 발견한다.
도구 메타데이터(readOnlyHint 등)를 어노테이션으로 함께 광고해 권한 분류(DAY 17 카탈로그)의 기초로 쓴다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 사유 |
|------|------|------|-----------|
| REST 직접 호출 (5월 방식) | 단순, 의존성 최소 | 도구 추가마다 Python 클라이언트 코드 수정, 스키마 이중 관리 (서버 API 스펙 ↔ 에이전트 tool 정의) | 도구가 늘어나는 로드맵과 정면 충돌 — 스키마 어긋남이 LLM 오호출로 직결 |
| 로컬 더미 유지 | 작업 0 | 데이터가 agent-service 에 갇힘, control-plane 의 존재 이유 상실 | 2주차 임시 조치였을 뿐, 실 데이터(DAY 20 보고서 축적) 연결 불가 |
| MCP 표준 (채택) | 스키마 서버 단일 관리, 도구 발견 자동, 표준 생태계(Inspector·인증 확장) 재사용 | 프로토콜 학습 비용, 서버 다운이 새 실패 지점 | — |

## 결과

- 쉬워지는 것: 도구 추가가 control-plane 한 곳 수정으로 끝난다 (Python 무수정 — DAY 16 실측 예정).
  MCP Inspector 로 에이전트 없이 도구를 검증할 수 있다 (DAY 15 실측 완료).
- 어려워지는 것: MCP 서버 다운이 에이전트 도구 호출의 새 실패 지점 — DAY 13 복원력 경로(재시도 →
  NodeFailure 기록 → 부분 진행)로 이어지는지 DAY 16 에 실측한다.
- 되돌리려면: 도구 로직은 평범한 Spring 빈이라 REST 컨트롤러로 재노출하면 된다 — 프로토콜 계층만 교체.
- 비교 실측(스키마 관리·클라이언트 코드량·토큰 비용)은 DAY 16 클라이언트 연동 후 이 문서에 보강한다.
