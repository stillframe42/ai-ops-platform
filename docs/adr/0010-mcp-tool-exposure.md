# ADR-0010: 운영 도구 노출 방식 — REST 직접 호출 대신 MCP 표준

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

분석 에이전트가 쓰는 운영 도구(배포 이력·유사 인시던트 검색·앱 설정)는 지금까지 agent-service 안의
로컬 더미 함수였다. 3주차에 control-plane 이 실체화되면서 이 도구들을 서버 측으로 이관하는데,
Python 에이전트가 Spring Boot 서버의 기능을 호출하는 방식을 정해야 한다. 제약 조건:

- 도구는 계속 늘어난다 (4주차 조치 실행, 8월 k8s 도구) — 추가할 때마다 양쪽 코드를 고치는 구조는 피하고 싶다
- 도구 스키마(이름·파라미터·설명)는 LLM 이 직접 소비한다 — 스키마 정의가 이중화되면 어긋난다
- 8월 보안 주간에 도구 접근 권한 체계(OAuth 2.1)를 얹을 예정 — 표준 위에 있어야 재사용할 게 많다

## 결정

control-plane 의 운영 도구를 **MCP(Model Context Protocol) 표준으로 노출**한다.
Spring AI 2.0 `spring-ai-starter-mcp-server-webmvc` (Streamable HTTP — SSE 는 2.0.0 부터 deprecated 라 사용 금지),
Python 쪽은 `langchain-mcp-adapters` 로 도구를 프로토콜로 발견한다.
도구 메타데이터(readOnlyHint 등)를 어노테이션으로 함께 광고해 권한 분류(DAY 17 카탈로그)의 기초로 쓴다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 사유 |
|------|------|------|-----------|
| REST 직접 호출 (5월 방식) | 단순, 의존성 최소 | 도구 추가마다 Python 클라이언트 코드 수정, 스키마 이중 관리 (서버 API 스펙 ↔ 에이전트 tool 정의) | 도구가 늘어나는 로드맵과 정면 충돌 — 스키마 어긋남이 LLM 오호출로 직결 |
| 로컬 더미 유지 | 작업 0 | 데이터가 agent-service 에 갇힘, control-plane 의 존재 이유 상실 | 2주차 임시 조치였을 뿐, 실 데이터(DAY 20 보고서 축적) 연결 불가 |
| MCP 표준 (채택) | 스키마 서버 단일 관리, 도구 발견 자동, 표준 생태계(Inspector·인증 확장) 재사용 | 프로토콜 학습 비용, 서버 다운이 새 실패 지점 (원격화 공통 — REST 직접 호출도 동일. MCP 고유분은 발견(tools/list) 의존 — 발견 시점 다운이면 도구가 목록에서 사라진다) | — |

## 결과

- 쉬워지는 것: 도구 추가가 control-plane 한 곳 수정으로 끝난다 (Python 무수정 — DAY 16 실측 예정).
  MCP Inspector 로 에이전트 없이 도구를 검증할 수 있다 (DAY 15 실측 완료).
- 어려워지는 것: MCP 서버 다운이 에이전트 도구 호출의 새 실패 지점 — 원격화 자체의 대가라
  REST 직접 호출이었어도 동일하고, MCP 고유분은 발견 층 의존이다 (2026-07-24 문답으로 보정).
  DAY 13 복원력 경로(재시도 → NodeFailure 기록 → 부분 진행)로 이어지는지 DAY 16 에 실측한다.
- 되돌리려면: 도구 로직은 평범한 Spring 빈이라 REST 컨트롤러로 재노출하면 된다 — 프로토콜 계층만 교체.
- 비교 실측(스키마 관리·클라이언트 코드량·토큰 비용)은 DAY 16 클라이언트 연동 후 이 문서에 보강한다.

## 추가 사항 (2026-07-24): DAY 16 클라이언트 연동 실측

Python 에이전트를 `langchain-mcp-adapters` 0.3.0 (`MultiServerMCPClient`, Streamable HTTP) 로
연결한 결과 — 기각한 REST 직접 호출 대안과의 비교 실측:

- **클라이언트 코드량**: 연결 구성 + 도구 발견 모듈(`app/tools/mcp_tools.py`) 약 20줄이 전부.
  도구별 코드가 0줄 — REST 방식이라면 도구 3종마다 tool 함수·스키마 정의·HTTP 호출 코드가 필요했다.
  기존 로컬 더미(`deployment_tools.py`)는 삭제.
- **스키마 서버 단일 관리 확인**: 서버의 한국어 설명·파라미터 스키마(`조회 대상 앱 이름 (현재 지원: target-app)`)가
  `tools/list` 로 그대로 내려와 LangChain 도구에 실림 — Python 쪽에 스키마 사본 없음.
  분석 실행에서 LLM 이 `getDeploymentHistory` 로 배포 상관을 배제하고 `searchSimilarIncidents` 로
  과거 사례(inc-2026-0412)와 대조해 가설을 기각/채택하는 것까지 확인 (확인 기준 충족).
- **도구 추가 시 Python 무수정**: 도구 이름이 클라이언트 코드에 없다 (발견 결과를 그대로 에이전트에 전달).
  control-plane 에 `@McpTool` 메서드를 추가하면 다음 발견 시점에 자동 반영된다.
- **서버 다운 실측 (결과 항목의 "새 실패 지점")**: 실패 지점이 두 층으로 나뉜다 —
  ① 발견(tools/list) 실패: 로컬 도구만으로 강등해 부분 진행 + 캐시 미보존으로 다음 실행에서 재발견 (실측: 그래프 오류 기록 없이 완주).
  ② 호출(tools/call) 실패: 전송 오류가 `ExceptionGroup(ConnectError)` 로 전파 → DAY 13 경로(NodeFailure 기록 → 부분 보고서) 동작 확인.
  단, ExceptionGroup 래핑 때문에 transient 재시도가 걸리지 않는 결함을 발견해 판정 로직에 그룹 해체를 추가했다.
- **인증**: `/mcp` 전용 API Key 헤더 필터 (`X-API-Key`, 키 미설정 시 인증 생략) — 무상태 왕복이라
  "요청마다 헤더 검사"로 충분. OAuth 2.1 전환은 8월 보안 주간.
- **토큰 비용 실측 (DAY 17 실험, count_tokens 기준)**: 도구 스키마는 LLM 호출마다 프롬프트에 반복
  포함된다 — 기준선(도구 0종) 1,129 토큰, 현재 5종 2,441 (+1,312), 15종 전체 노출 3,711 (+2,582).
  15종 시나리오에서 관련 도구만 선별(7종)하면 호출당 968 토큰 절감 — ReAct 루프 왕복 수만큼 배가되므로
  도구가 늘수록 점진적 노출(발견 결과를 필터링해 에이전트에 바인딩)이 유효하다. 어댑터가 도구를
  평범한 리스트로 반환하므로 프로토콜 변경 없이 클라이언트 선별로 구현 가능.
