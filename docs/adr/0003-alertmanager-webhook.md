# ADR-0003: 감지 트리거 방식 — Alertmanager 룰 기반 웹훅

- 상태: 승인됨
- 날짜: 2026-07-14

## 맥락

모니터링 에이전트가 target-app 의 이상을 어떻게 감지할지가 미결이었다 ([scenarios.md](../scenarios.md) ADR-0003 예약). 선택지는 두 가지다.

1. **폴링**: 에이전트가 Prometheus 를 주기적으로 PromQL 조회하고 스스로 임계값을 판정
2. **룰 기반 웹훅**: Prometheus Alert Rule 이 임계값을 판정하고, Alertmanager 가 webhook 으로 에이전트에 통지

infra 구성(DAY 6)에 Alertmanager 포함 여부가 걸려 있어 지금 결정이 필요하다. 제약 조건: 시나리오 1·2 의 트리거는 지속 시간 조건(5분/3분)과 중복 알림 억제를 요구하고, 시나리오 3 의 트리거(GC 후 heap 의 30분 창 선형 회귀 우상향)는 단순 PromQL 룰로 표현하기 어렵다.

## 결정

**Alertmanager 룰 기반 웹훅을 채택한다.** 임계값형 트리거(시나리오 1·2)의 1차 판정은 Prometheus Alert Rule 이 담당하고, 모니터링 에이전트의 역할은 "판정"에서 "webhook 수신 → 감지 이벤트 정규화 → 분석 위임"으로 조정한다. 예외로 추세형 트리거(시나리오 3)는 에이전트의 범위 쿼리 판정을 유지하며, heap 사용률 > 85% 룰을 순간 위험 안전망으로 병행한다 — 즉 정확한 형태는 "임계값형은 룰, 추세형은 에이전트"의 하이브리드다. webhook 수신자(agent-service)가 구현되기 전까지는 receiver 를 placeholder 로 두고 Alertmanager UI 로 발화를 확인한다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 사유 |
|------|------|------|-----------|
| 폴링 (에이전트가 판정) | 임계값을 에이전트가 동적 조정 가능, 판정 로직에 LLM 개입 여지 | 상시 폴링 루프 구동, 지속 시간 판정·중복 억제·그룹핑을 에이전트가 재구현, 감지 파이프라인을 독립 검증할 수단 없음 | Prometheus 생태계가 이미 제공하는 기능(`for:`, inhibition, grouping)의 재발명. 표준 알림 파이프라인 학습 가치도 웹훅 쪽이 큼 |
| 전부 룰 기반 (시나리오 3 포함) | 감지 경로 단일화 | 선형 회귀·다중 GC 사이클 일관성 같은 추세 판정을 PromQL 룰로 표현 곤란 (`deriv` 근사는 오탐 구분 불가) | 시나리오 3 의 "스파이크와 구분" 요구를 충족 못함 |

## 결과

- 쉬워지는 것: 지속 시간 판정·중복 억제·그룹핑이 설정으로 해결, 에이전트 단순화(수신·정규화만), Alert Rule 만으로 감지 파이프라인을 에이전트 없이 독립 검증 가능 (DAY 6 확인 기준이 이 성질에 의존).
- 어려워지는 것: 임계값 변경이 infra 설정 변경(룰 파일 수정 + 리로드)이 됨 — 에이전트가 런타임에 임계값을 조정할 수 없다. 필요해지면 이 ADR 을 재검토. webhook 수신 실패 대비는 Alertmanager 재시도 설정에 의존.
- 되돌리기: 에이전트에 폴링 루프를 추가하면 됨. 기존 Alert Rule 은 안전망으로 남길 수 있어 전환 비용 낮음.
