# ADR-0012: 에이전트 간 통신에서 A2A 검토

- 상태: 승인됨
- 날짜: 2026-08-06

## 맥락

4주차에 승인 사이클(HITL)이 완성되면서 에이전트 간 통신 구조가 확정 형태를 갖췄다: 시스템 내부는 Kafka 이벤트(`ops.incidents` / `ops.actions.pending` / `ops.actions.decisions` / `ops.analysis.results`, ADR-0011·0005)로, 에이전트-도구 연결은 MCP(ADR-0010)로 통신한다. 같은 시기 A2A(Agent2Agent) 프로토콜이 스펙 v1.0 에 도달하며 (2026-04 릴리스, Linux Foundation 관리, 150+ 조직 참여) "에이전트 간 통신의 표준"으로 자리 잡고 있어, 현행 구조와의 관계를 판단할 필요가 생겼다.

원안은 실험 전에 "A2A 채택·커스텀 REST 폐기"를 결론으로 적고 있었으나, 주간 계획 수립 시 "실측 비교 후 판단"으로 변경했다 (weekly-plan 순서 검토 ①). 근거: ① 현 구조에는 A2A 가 전제하는 조직·시스템 경계가 없다 (프로세스 내 LangGraph state 공유 + 시스템 내 Kafka/MCP 계약) ② 동기 위임 전환은 3주차에 실측한 오프셋 층 무유실(6.5분 다운 → +52초 회복)을 포기하는 방향 ③ 승인 도메인 상태(`PROCESSING/DONE/FAILED` 계열)는 감사와 결합한 도메인 소유라 A2A task 전송 상태의 대체 대상이 아니다.

실험은 1일 축소판으로 실시했다 (2026-08-06, `feature/a2a-experiment` 브랜치 — merge 하지 않고 유지):

- **스펙·SDK 확정 (Phase 0 잔여)**: 스펙 v1.0 (서명 Agent Card 는 8.4절 정식 포함, 전송 바인딩 JSON-RPC/gRPC/REST 3종), `a2a-sdk`(Python) 1.1.2 (2026-07-22)
- **샘플 실측**: 에코 에이전트로 Agent Card 발견(`/.well-known/agent-card.json`) → `message/send` 위임 → 스트리밍 수신(submitted → working → artifact → completed) 완주
- **Supervisor 노출 실측**: `IncidentAnalysisExecutor`(monitor → analysis 노드 실행)를 AgentExecutor 어댑터로 감싸 aiops-supervisor / skill: incident-analysis 로 노출 — 기존 FastAPI·Kafka 경로와 병행, 대체 아님. chaos error-rate 30% 상태에서 분석 태스크 위임 1건 **37초 완주** (P2·confidence 0.95 보고서 아티팩트 + 진행 상태 스트리밍 수신), 화이트리스트 밖 시나리오는 `rejected` 종결

## 결정

**현 시스템의 에이전트 간 통신에 A2A 를 채택하지 않는다.** 내부 통신은 Kafka 이벤트 + MCP 도구 노출을 유지하고, A2A 는 아래 "채택이 유효해지는 경계 기준"에 도달하는 시점에 재검토한다. 실험 브랜치(`feature/a2a-experiment`)는 merge 하지 않고 참조용으로 유지한다.

## MCP / A2A 역할 분담 (실측 후 정리)

| | MCP | A2A |
|---|---|---|
| 통합 방향 | 수직 — 에이전트가 도구·컨텍스트를 소비 | 수평 — 불투명한(opaque) 에이전트 간 태스크 위임 |
| 노출 단위 | 도구(tool)·리소스 | 스킬(skill) + 태스크 수명주기 |
| 상대에 대한 가정 | 호출자가 도구 스키마를 알고 조합 | 상대 내부 구현을 모름 — Agent Card 로 발견 |
| 이 프로젝트에서 | control-plane 이 운영 도구 서버 (ADR-0010) | (미채택) Supervisor 를 위임 대상으로 노출하는 실험만 |

두 프로토콜은 경쟁 관계가 아니라 계층이 다르다. 이 프로젝트의 분석 에이전트는 MCP 로 도구를 소비하면서, 실험에서는 동시에 A2A 서버(위임 수신자)였다 — 한 에이전트가 양쪽에 동시에 설 수 있다.

## 비교 기준표 — Kafka(현행) / REST 직결(가정) / A2A (실측)

| 기준 | Kafka (현행, ADR-0011) | REST 직결 (가정) | A2A (실험 실측) |
|------|------|------|------|
| 상태 관리 | 도메인 소유 — 승인·감사 상태는 DB(action_approvals), 실행 상태는 체크포인터 (ADR-0009) | 별도 구현 | 프로토콜 표준 태스크 상태 9종 — `input-required` 는 승인 대기(interrupt)와 개념 대응, 단 감사·타임아웃 정책은 여전히 도메인 몫 |
| 다운 중 무유실 | **브로커 보존 — 3주차 실측: 6.5분 다운 → 재기동 +52초 회복** | 없음 — 수신자 다운 = 유실 (재시도 직접 구현) | 없음 — 동기 세션. 서버 부재 시 재시도 주체가 클라이언트로 이동. TaskStore 영속화(DatabaseTaskStore)는 수신 후 상태만 보존 |
| 재처리 | 오프셋 되감기 + 처리 측 멱등 2층 | 별도 구현 | 태스크 재조회(`tasks/get`)는 있으나 재실행 의미론은 클라이언트 재위임 |
| 폭주 흡수 | 배치 + Semaphore 백프레셔 (LLM 비용 상한) | 별도 구현 | 서버 측 동시성 제어 별도 구현 (프레임워크는 요청 단위) |
| 타 프레임워크 연동 | 계약 = 토픽 페이로드 (자체 정의, 문서로 공유) | 계약 = OpenAPI (자체 정의) | **표준 — Agent Card 발견 + 스킬 선언으로 상대 프레임워크와 무관하게 위임 가능** (LangGraph 내부 구현이 완전히 은폐됨을 실측) |
| 성숙도 | 운영 실적 광범위 | — | 스펙 v1.0 안정, 조직 참여 확대. 단 SDK 는 v1.x 에서 pydantic → protobuf 전면 전환으로 v0.2 예제 비호환, Task 이벤트 선행 enqueue 규약 등 문서 밖 관례를 소스에서 확인해야 했다 (실측) |
| 코드량 (agent-service 측) | 344줄 — 트리거 소비·결정 소비·소비 루프·발행 (`app/events/`) | — | 227줄 — 어댑터 142 + 서버 엔트리 23 + 클라이언트 62. **범위 주의: Kafka 는 트리거→재개→결과 발행 전 사이클, A2A 는 분석 위임 1건 경로만** — 동등 범위 비교가 아니다 |
| 복잡도 (정성) | 오프셋·멱등 2층 설계 학습 비용 (기지불) | 낮음 | 어댑터 자체는 낮음 (반나절 구현). 무유실·백프레셔를 요구하는 순간 Kafka 가 제공하던 성질의 재구현이 시작된다 |

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 사유 |
|------|------|------|-----------|
| A2A 로 내부 통신 전환 | 표준 준수, 타 프레임워크 연동 표준화, 태스크 상태·스트리밍 내장 | 오프셋 층 무유실·재처리·백프레셔 상실 (재구현 필요), 승인·감사 도메인 상태는 어차피 대체 불가, 내부에 경계가 없어 발견(Agent Card)의 이득이 없음 | 현 구조의 필요 성질(ADR-0011 ①~④)을 잃고 얻는 것이 내부에서는 없다 |
| A2A 병행 상시 노출 (실험 구성 유지) | 외부 위임 진입점 확보 | 호출자가 없는 진입점 유지 비용 (인증·버전·테스트), 승인 흐름 밖 실행 경로가 상시 존재 | 수요(외부 에이전트) 발생 전에는 표면만 넓힌다 — 경계 기준 도달 시 재개 |
| 미채택 + 경계 기준 기록 (채택) | 현행 성질 유지, 재검토 조건 명문화, 실험 코드는 브랜치로 보존 | 표준 선행 학습의 리듬을 잃을 수 있음 | — |

## 채택이 유효해지는 경계 기준

다음 중 하나에 도달하면 A2A 도입을 재검토한다. 공통 성질: **우리가 내부 계약(Kafka 토픽·LangGraph state)을 공유할 수 없는 상대**가 생기는 시점.

1. **조직 밖 개방** — 외부 조직의 에이전트가 이 플랫폼에 분석·조치를 위임하거나 그 역방향이 필요할 때 (그때는 서명 Agent Card·보안 스킴이 스펙에 이미 준비돼 있음을 확인)
2. **시스템 경계 밖 다른 스택의 에이전트** — 사내라도 별도 배포 단위·다른 프레임워크(예: 타 팀 ADK/CrewAI 에이전트)가 위임 상대가 될 때 — Agent Card 발견이 계약 문서 공유를 대체
3. **`input-required` 왕복이 프로토콜 경계를 넘어야 할 때** — 승인 대기 중인 태스크를 외부 위임자가 표준 상태로 관찰·재개해야 할 때 (현 Slack 승인은 시스템 내부 채널이라 해당 없음)

재검토 시 실험 브랜치의 어댑터(`app/a2a/server.py` — 키-게이트 `A2A_ENABLED` 병행 마운트)가 출발점이다.

## 결과

- 쉬워지는 것: 내부 통신의 성질(무유실·재처리·백프레셔·감사 결합)을 그대로 유지, A2A 는 실측 근거를 가진 재검토 조건으로 관리
- 어려워지는 것: 외부 연동 요구가 갑자기 오면 어댑터 승격 + 인증·서명 카드 검토가 그때 일괄 필요 (실험 브랜치가 리드타임을 줄인다)
- 되돌리기: 채택으로 돌아서는 비용이 낮다 — 어댑터가 노드 호출부와 분리돼 있어 (monitor/analysis 직접 호출) 그래프·이벤트 경로 무변경으로 병행 노출만 켜면 된다
