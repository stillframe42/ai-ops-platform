# 시스템 시나리오

플랫폼이 E2E 로 데모해야 하는 시나리오 3종을 정의한다. 각 시나리오는 ①트리거 조건(정량 임계값) ②에이전트 흐름 ③산출물 ④데모 확인 방법 4요소를 갖춰야 완성으로 본다.

임계값 수치는 데모 기준 기본값이며, 전부 agent-service 설정값으로 노출한다 (데모 시연 시간 단축을 위해 조정 가능해야 함).

## 에이전트 역할과 책임 경계

시나리오에 등장하는 에이전트는 3종이다. 여기 없는 역할(예: 배포, 코드 수정)은 이 플랫폼의 범위 밖이다.

### 모니터링 에이전트 — 감지

- 책임: target-app 의 메트릭에서 트리거 조건 충족을 감지하고, 감지 이벤트(시나리오 종류·시각·근거 수치)를 만들어 분석 에이전트에게 넘긴다.
- 하지 않는 것: 원인 판단, 조치 제안. 감지와 판단을 분리해 오탐 분석을 가능하게 한다.
- 감지 방식: **Alertmanager 룰 기반 웹훅 수신** ([ADR-0003](adr/0003-alertmanager-webhook.md)) — 임계값형 트리거(시나리오 1·2)의 1차 판정은 Prometheus Alert Rule 이 담당하고, 에이전트는 webhook 을 받아 감지 이벤트로 정규화한다. 추세형 트리거(시나리오 3)는 예외로 에이전트의 범위 쿼리 판정을 유지한다.

### 분석 에이전트 — 원인 조사

- 책임: 감지 이벤트를 받아 관측 데이터를 조사하고 원인 보고서를 생성한다.
- 조회 가능한 데이터 소스:
  - 메트릭: Prometheus (범위 쿼리 포함 — 시나리오 3의 추세 분석에 필요)
  - 로그: **Loki (LogQL)** — 도입 확정 ([ADR-0004](adr/0004-loki-adoption.md)). 단 에이전트의 직접 조회 도구는 2단계(에이전트 day 결정) — 도구 도입 전까지 보고서의 로그 근거는 Grafana Explore 링크로 대체
  - 히스토리(과거 장애·조치 이력): 데모 범위는 **Prometheus 기본 보존으로 충분** — 별도 저장소는 보류 ([ADR-0004](adr/0004-loki-adoption.md)), "과거 유사 장애 검색" 확장 시 재검토
- 데이터 접근 경로: **직접 조회** — agent-service 가 Prometheus/Loki HTTP API 를 직접 호출 ([ADR-0002](adr/0002-observability-access-path.md)). 읽기는 직접, 조치 실행 경로는 별도(ADR-0005).

### 실행 에이전트 — 조치 제안·실행

- 책임: 분석 결과를 근거로 대응 조치를 제안하고, 승인된 조치만 실행한다.
- 허용 조치 화이트리스트 (이 목록 밖의 조치는 제안 자체가 불가 — 구현은 `ActionType` 카탈로그와 1:1, 2026-07-21 정합):

  | 조치 (카탈로그) | 의미 | 대상 | 승인 필요 |
  |------|------|------|-----------|
  | NOTIFY_ONLY | 알림·보고만 (상태 변경 없음) | - | 불필요 |
  | RESTART_APP | 컨테이너 재시작 | target-app | **필수** |
  | SCALE_OUT | 스케일아웃 (replica 증가) | target-app | **필수** |
  | ROLLBACK | 직전 버전으로 롤백 | target-app | **필수** |
  | CIRCUIT_BREAK | 트래픽 차단·격리 (서킷 브레이커) | target-app | **필수** |

  진단 정보 수집(스레드 덤프 등 읽기 전용)은 조치가 아니라 분석 단계의 도구로 흡수됐다.

- 승인 경계 원칙: **대상 시스템의 상태를 바꾸는 모든 조치는 human-in-the-loop 승인 필수.** 읽기 전용 조치와 알림·보고서 발송은 승인 없이 수행한다.
- 조치 실행의 권한 주체(docker API 접근을 agent-service 가 직접 갖나, control-plane 이 대행하나)는 **미결** ([ADR-0005 예약](#미결-사항--adr-후보)).

## 시나리오 1: latency 급증 — 감지·분석·보고

### ① 트리거

- target-app HTTP 요청의 **p95 latency ≥ 3초**가 **5분간 지속**
- 최소 표본 조건: 해당 5분간 요청 수 ≥ 30건 (표본 부족 시 판정 보류 — 저트래픽 오탐 방지)

### ② 흐름

1. 모니터링 에이전트가 트리거 충족을 감지, 감지 이벤트 생성
2. 분석 에이전트가 조사: latency 분포(엔드포인트별 p50/p95/p99), 동시간대 CPU/메모리/스레드 풀 메트릭, (Loki 도입 시) 해당 구간 에러·경고 로그
3. 원인 보고서 생성 → control-plane 경유 Slack 채널로 발송

이 시나리오는 조치 실행이 없다 — 감지→분석→보고 파이프라인 자체의 검증이 목적.

### ③ 산출물: 원인 보고서

보고서 포맷 (Slack 메시지 + 상세 첨부, 이후 모든 보고서의 공통 골격):

| 절 | 내용 |
|----|------|
| 요약 | 무슨 일이 언제부터 — 1~2문장 |
| 근거 메트릭 | 판정에 사용한 수치·기간, Grafana 패널 링크 |
| 추정 원인 | 조사 결과 기반 가설 (확신도 표기: 높음/중간/낮음) |
| 권고 | 사람이 취할 다음 행동 제안 |

### ④ 데모 확인 방법

1. fault-injection 으로 지연 주입 (`FI-1`, 아래 요구사항 참조)
2. 트리거 지속 시간 경과 후 Slack 에 원인 보고서 도착 확인
3. 보고서의 "근거 메트릭"이 Grafana 에서 실제 재현되는지 대조
4. 주입 해제 후 재감지가 발생하지 않는 것 확인 (중복 알림 억제 검증)

## 시나리오 2: 에러율 급증 — human-in-the-loop 조치

### ① 트리거

- target-app HTTP 응답 중 **5xx 비율 ≥ 10%**가 **3분간 지속**
- 최소 표본 조건: 해당 3분간 요청 수 ≥ 30건

### ② 흐름

1. 모니터링 에이전트 감지
2. 분석 에이전트가 조사 후 원인 보고서 생성 (시나리오 1과 동일 포맷)
3. 실행 에이전트가 화이트리스트 내에서 조치 제안 (예: 컨테이너 재시작) — 제안에는 근거·예상 효과·리스크 포함
4. control-plane 이 승인 요청을 사람에게 전달 → **승인 대기** (타임아웃 정의 필요: 기본 10분, 미응답 시 조치 폐기 + 알림만 유지)
5. 승인 시: 실행 에이전트가 조치 실행 → 실행 결과와 회복 여부(트리거 조건 해소)를 보고
6. 거부 시: 조치 폐기, 거부 사실과 사유를 이력에 기록

승인 UX(버튼 인터랙션이 필요하므로 Slack incoming webhook 으로는 불가)는 **미결** ([ADR-0006 예약](#미결-사항--adr-후보)).

### ③ 산출물

- 원인 보고서 (시나리오 1 포맷)
- 조치 제안서: 제안 조치 / 근거 / 예상 효과 / 리스크 / 승인 기한
- 실행 결과 보고: 수행 내용 / 수행 시각 / 회복 여부 (조치 후 트리거 조건 재평가 결과)

### ④ 데모 확인 방법

1. fault-injection 으로 에러율 주입 (`FI-2`)
2. 승인 요청 수신 → **승인 경로**: 승인 후 target-app 컨테이너가 실제 재시작되고 에러율이 정상화되는 것 확인 (재시작이 주입 상태를 초기화하므로 회복이 데모됨)
3. 재주입 후 **거부 경로**: 거부 시 조치가 실행되지 않고 기록만 남는 것 확인
4. **타임아웃 경로**: 미응답 시 조치가 폐기되는 것 확인

## 시나리오 3: 메모리 누수 패턴 — 히스토리 기반 분석

### ① 트리거

단발 스파이크와 구분하기 위해 **GC 직후 heap 사용량**(old gen, full/major GC 후 값)의 추세를 본다. GC 전 값은 정상 상태에서도 톱니파라 우상향 판정이 무의미하다.

- **30분 관측 창**에서 GC 직후 heap 사용량의 선형 회귀 기울기가 양수이고, 창 시작 대비 **20% 이상 증가**
- 스파이크 구분 조건: 창 내 최소 3회 이상의 GC 사이클에서 일관되게 상승 (1회성 급증 배제)
- 역할 분담: 순간 위험(heap 사용률 > 85%)은 Prometheus Alert Rule 이 안전망으로 별도 감지한다 ([ADR-0003](adr/0003-alertmanager-webhook.md)) — 본 시나리오의 추세 감지는 에이전트 담당

### ② 흐름

1. 모니터링 에이전트 감지 (범위 쿼리 기반 — 순간값이 아닌 추세 판정)
2. 분석 에이전트가 히스토리 기반 조사: 증가 시작 시점, 시작 시점 전후의 배포·조치 이력, 현재 증가율 기준 OOM 예상 도달 시각
3. 누수 의심 보고서 생성 → Slack 발송. 조치 제안은 하지 않는다 (재시작은 증상 완화일 뿐이고, 누수는 사람의 코드 조사가 필요 — 권고란에 명시)

히스토리 저장소(Prometheus 보존 기간으로 충분한가 vs 별도 DB)는 **미결** ([ADR-0004 예약](#미결-사항--adr-후보)) — 데모 범위(30분 창)에서는 Prometheus 기본 보존으로 충분하나, "과거 유사 장애 검색"까지 확장하면 별도 저장이 필요해진다.

### ③ 산출물: 누수 의심 보고서

공통 보고서 골격 + 추가 항목:

- 추세 근거: 관측 창의 GC 후 heap 그래프 (Grafana 패널 링크)
- 예측: 현재 증가율 유지 시 OOM 예상 도달 시각
- 권고: 증상 완화(재시작 시점 제안)와 근본 원인 조사(heap dump 채취 안내)를 구분해 제시

### ④ 데모 확인 방법

1. fault-injection 으로 누수 시뮬레이션 시작 (`FI-3`)
2. 관측 창 경과 후 누수 의심 보고서 도착 확인 (데모용으로 관측 창을 5분까지 단축 가능해야 함 — 설정값)
3. 보고서의 OOM 예측 시각이 주입 증가율과 정합하는지 확인
4. **음성 테스트**: 단발 스파이크(대량 요청 후 회복)에서는 트리거되지 않는 것 확인

## 시나리오 역산: target-app fault-injection 요구사항

각 시나리오를 데모하려면 장애를 일부러 낼 수단이 필요하다. target-app 설계 day 의 입력.

| ID | 기능 | 요구사항 | 데모 대상 |
|----|------|----------|-----------|
| FI-1 | 지연 주입 | 지연 시간(ms)과 적용 비율(%)을 지정해 응답 지연. 런타임 토글 (재시작 없이 on/off) | 시나리오 1 |
| FI-2 | 에러 주입 | 지정 비율(%)의 요청에 5xx 응답. 런타임 토글 | 시나리오 2 |
| FI-3 | 메모리 누수 시뮬레이션 | 분당 증가량(MB/min)을 지정해 heap 을 점진 점유. 시작/중지 가능, 중지 시 해제 | 시나리오 3 |
| FI-4 | 주입 상태 조회/일괄 해제 | 현재 활성 주입 목록 조회 + 전체 해제 | 데모 리셋 |

공통 요구사항:

- 주입 상태는 인메모리로 충분 (재시작 시 초기화 — 시나리오 2의 "재시작으로 회복" 데모가 이 성질에 의존한다)
- 비율 기반 트리거(시나리오 1·2의 최소 표본 조건)를 채우려면 **상시 기본 트래픽 발생원**이 필요 — 부하 생성기(스크립트 or 컨테이너)를 infra day 입력으로 함께 인계
- fault-injection 엔드포인트 자체는 관리용으로 분리 (모니터링 대상 트래픽 통계에 섞이지 않도록 별도 포트 또는 경로 그룹)
